什麼是 MCP？

一套讓 AI 應用能以共同規則連接外部工具與資料的開放協定。

MODEL
Context
Protocol.

不是新模型，不是萬能外掛。
它解決的是「如何連接」這件事。

WHAT一套連接協定

讓 AI 應用與外部能力溝通。

WHOHost · Client · Server

三種角色協作完成對接。

WHY減少重複整合

不同工具遵循相同溝通規則。

05 / TRANSPORT
05 / 12

MCP Server 不一定在雲端

同一份協定能力，可以透過不同傳輸方式送出訊息。

⌨

本機：stdio

Host ⇄ 本機 Server

以程式的標準輸入／輸出交換訊息。

例：本機檔案工具
◎

遠端：Streamable HTTP

Host ⇄ 遠端 Server

以網路傳遞請求，需要考慮認證與安全。

例：遠端企業服務
Transport 負責「怎麼傳」，MCP Data Layer 負責「傳什麼意思」。

06 / SERVER CAPABILITIES
06 / 12

Server 的三大能力

Tools 是動作、Resources 是資料、Prompts 是可重用的互動模板。

01

Tools

做一件事

讓應用呼叫可執行功能，可能產生副作用。

例如：查詢 Issues
tools/list → tools/call
02

Resources

讀取資訊

提供上下文資料給應用使用。

例如：專案 README
resources/list → read
03

Prompts

使用模板

提供預先設計好的互動提示流程。

例如：Issue 摘要格式
prompts/list → get

以上 GitHub 能力是教學範例，並非每個 GitHub MCP Server 都必定提供全部三種能力。

07 / WIRE FORMAT
07 / 12

JSON-RPC：訊息的基本形狀

MCP 使用 JSON-RPC 2.0 表達請求與回應，但這不等於模型自己輸出 JSON 就完成 MCP。

概念示意 · 不是可直接送出的完整 MCP 2026 訊息
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/list",
  "params": {}
}
jsonrpc

訊息使用的 RPC 版本

id

識別這個請求及其回應

method

想執行的協定操作

params

這次操作帶入的資料

2026-07-28 採無狀態核心；實際請求還須依規範攜帶 _meta 等資訊。舊版 initialize 不再是新版必經握手。

MCP ≠ API ≠ Function Calling

三者不在同一層，但可以協作完成一次 AI 工具呼叫。

01

Function Calling / Tool Calling

模型提出「想用哪個工具、帶什麼參數」。

↓
02

MCP

Host 的 Client 依共同協定發現、呼叫外部 Server。

↓
03

API / 後端服務

Server 在背後使用現有 API 或其他系統能力。

這是教學性架構推論，不是官方規範要求的唯一實作方式。

10 / COMPARISON
10 / 12

那 MCP 和 RAG 又差在哪裡？

RAG 解決「回答前如何找資料」，MCP 解決「應用如何標準化連接資料／工具」。

RETRIEVAL STRATEGY

RAG

檢索相關內容，再提供給模型生成回答。

問題 → 找文件 → 回答
INTEGRATION PROTOCOL

MCP

讓應用依共同協定使用外部資料與工具。

Client → Server → 外部能力
可以一起用

例如：RAG 系統透過 MCP Tool 存取外部搜尋服務，回傳的結果再作為回答脈絡。

本頁為教學性比較，MCP 與 RAG 沒有必然依賴關係。

11 / SECURITY
11 / 12

接上真實工具，也接上真實風險

MCP 標準化的是連接方式，不會自動保證 Server 可信或授權安全。

🔑

最小權限

只授予完成這次任務所需的權限。

🛡

Token 驗證

核對對象與用途，避免盲目轉送憑證。

🌐

SSRF 防護

限制可存取網路目標，避免走進內部服務。

🧭

使用者同意

高風險操作應有明確核准與拒絕路徑。

是否允許建立 Issue、修改檔案或傳送資料，是系統權限問題，不該全交由模型猜測。
